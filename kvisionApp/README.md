# kvisionApp

KVision browser UI (Kotlin/JS). Compiles to one JS bundle that runs in
Chromium / Firefox / Safari / Electron. Talks to the dedicated game server
via the WebSocket RPC bridge on `ws://127.0.0.1:9080/events`.

```
src/jsMain/kotlin/
├── org/ttt/autogenesis/kvisionapp/
│   ├── Main.kt                              ← entry point
│   ├── PushNotificationService.kt           ← Service Worker + Web Push subscription
│   ├── WebSocketRpcBridge.kt
│   └── ResumeAvailabilityListener.kt
└── ui/
    ├── MainMenu.kt
    ├── GameplayUI.kt
    ├── ...
src/jsMain/resources/
├── sw.js                                    ← copied to /sw.js by webpack pwa-push hook
├── manifest.webmanifest                     ← served at /manifest.webmanifest
└── index.html
webpack.config.d/
└── pwa-push.js                               ← emits sw.js + manifest.webmanifest
build/generated/vapid/
└── vapid_public.json                        ← generated by :kvisionApp:generateVapidKeys
```

## Build & run

```bash
# Production bundle (used by /build/dist/js/productionExecutable/)
./gradlew :kvisionApp:jsProductionExecutable
./gradlew :kvisionApp:jsBrowserProductionWebpack     # webpack bundling step

# Dev mode (HMR + watch) — see "Node 22+ webpack-cli gotcha" below
./gradlew :kvisionApp:jsBrowserDevelopmentRun

# Local static serve of the production bundle, used by the e2e probes:
node kvisionApp-e2e/static-server-8080.mjs
```

## Web Push plumbing (browser side)

The browser-side push pipeline lives entirely in
`src/jsMain/kotlin/org/ttt/autogenesis/kvisionapp/PushNotificationService.kt`.
Three subtle Kotlin/JS interop quirks made it disappear from the
production bundle in the past — they're pinned here so future edits
don't reintroduce them.

### 1. DCE keepalive (production bundle tree-shake hazard)

The Play button in `ui/MainMenu.kt` invokes
`PushNotificationService.subscribeIfPermitted()` through a KVision
`onClick { ... }` lambda — which the Kotlin/JS linker can't see through
statically. Without a direct top-level reference, the entire
`PushNotificationService` object was dead-code-eliminated from the
production webpack bundle and the subscription never fired.

`src/jsMain/kotlin/org/ttt/autogenesis/kvisionapp/Main.kt` pins a
top-level reference inside `start()`:

```kotlin
// DCE keepalive — see Main.kt comment block
val pushServiceKeepalive: Any = PushNotificationService
```

**Do not delete that line.** If you do, the linker's static analysis will
tree-shake `PushNotificationService`, `sw.js`, and the VAPID
`applicationServerKey` fetch path out of the bundle. Symptoms: no
Service Worker registration in the browser console, no
`PushSubscription`, `TurnHarness.executeSingleTurn` push trigger
silently no-ops.

Verify the bundle still contains the symbols:

```bash
grep -o 'PushNotificationService\|unsafeCast\|subscribeIfPermitted\|vapid_public\|/sw.js' \
  kvisionApp/build/dist/js/productionExecutable/kvisionApp.js | sort -u
```

You should see all five. If `PushNotificationService` or
`subscribeIfPermitted` is missing, the keepalive was removed.

### 2. `.await()` on `dynamic` Promise values

`nav.serviceWorker.register(...)`, `nav.serviceWorker.ready`,
`Notification.requestPermission()`, and
`registration.pushManager.subscribe(...)` are all `dynamic` in
Kotlin/JS — the standard library bindings don't surface the modern
Service Worker / Push API types. Calling `.await()` directly on `dynamic`
fails at runtime with `(...).await is not a function`.

The fix in `PushNotificationService.kt`:

```kotlin
val registerPromise: Promise<dynamic> =
    nav.serviceWorker.register(SW_PATH).unsafeCast<Promise<dynamic>>()
val reg = registerPromise.await()
```

Same pattern for `ready`, `requestPermission`, and `subscribe`. Do not
revert to the bare `.await()` form.

### 3. `sw.js` and `/vapid_public.json` must be served alongside the bundle

The Service Worker registers from the **scope of `/`** (the page loaded
at `http://localhost:8080/index.html`). Both files MUST be reachable at
`/sw.js` and `/vapid_public.json` respectively:

| URL path       | Source file                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------- |
| `/sw.js`       | `kvisionApp/build/processedResources/js/main/sw.js` (copied by the webpack `pwa-push` hook) |
| `/manifest.webmanifest` | Same — emitted by `pwa-push.js`                                                  |
| `/vapid_public.json` | `kvisionApp/build/generated/vapid/vapid_public.json` (from `:kvisionApp:generateVapidKeys`) |

The production webpack output (`build/dist/js/productionExecutable/`)
does **not** contain these — webpack emits only the JS bundle. The
`kvisionApp-e2e/static-server-8080.mjs` fallback server overlays them.
See `kvisionApp-e2e/README.md` for why.

## Node 22+ webpack-cli gotcha

`./gradlew :kvisionApp:jsBrowserDevelopmentRun` (and
`jsBrowserProductionWebpack`) **fail on Node 22+** with:

```
SyntaxError: Identifier 'path' has already been declared
    at wrapSafe (node:internal/modules/cjs/loader:...)
    at WebpackCLI.tryRequireThenImport (.../webpack-cli/lib/webpack-cli.js:225:30)
```

Root cause: the auto-generated `kvisionApp/build/js/packages/.../webpack.config.js`
ends up with two `const path = require('path');` declarations because
`kvisionApp/webpack.config.d/pwa-push.js` declares one and the
KVision-generated prelude declares another.

`webpack-cli` 6.x loads the file as ESM, so the two `const path`
declarations collide in one module scope. The CI image runs Node 16 /
18; local machines often run Node 22+.

**Workaround (used today):** invoke webpack directly with the
auto-generated config after a deduplication pass. The
`kvisionApp-e2e/static-server-8080.mjs` ships the production bundle, so
the dev webpack pipeline is not on the critical path. Two options:

1. **Run webpack directly** (one-off):
   ```bash
   # Dedupe the duplicated `const path =` first:
   sed -i 's|^const path = require.path.;$|const path2 = require("path");|' \
     kvisionApp/build/js/packages/Autogenesis-kvisionApp/webpack.config.js
   cd kvisionApp/build/js/packages/Autogenesis-kvisionApp
   node ../../node_modules/webpack/bin/webpack.js --config webpack.config.js
   ```
   (This is how the production webpack bundle was rebuilt during the
   push-notification probe work.)

2. **Use the fallback static server** (no webpack at all):
   ```bash
   node kvisionApp-e2e/static-server-8080.mjs
   ```
   This serves `build/dist/js/productionExecutable/` (which is already
   committed once CI built it) plus `sw.js`, `vapid_public.json`, and
   `manifest.webmanifest` overlaid from `build/processedResources`.

If you upgrade `webpack-cli` past 6.0.1, the underlying ESM-vs-CJS
collision may go away. Until then, do not delete
`kvisionApp-e2e/static-server-8080.mjs` — it's how local Node 22+
machines get a working UI without a webpack dev server.

## Service Worker registration timing

`PushNotificationService.registerServiceWorker()` is called eagerly
from `Main.start()` — see `Main.kt` around line 83. The
`navigator.serviceWorker.ready` await is required before
`PushManager.subscribe()` will succeed; the code awaits it
correctly, so don't skip that step.

The Service Worker registration fails (and the rest of the pipeline
short-circuits) if `/sw.js` returns 404. Symptom:
`PushNotificationService: SW registration failed: ...`. Start by
hitting `curl http://127.0.0.1:8080/sw.js` and confirm 200.

## VAPID public-key provisioning

The public key the browser uses as `applicationServerKey` is generated
and shipped by:

```bash
./gradlew :kvisionApp:generateVapidKeys
```

Outputs:

| File                                                       | What it is                                                                                       |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `~/.autogenesis/vapid_private.pem`                         | Private key, SEC1 PEM, 0600 perms. Consumed by the **server** (`PushVapidConfig.loadKeypair`).    |
| `kvisionApp/build/generated/vapid/vapid_public.json`      | Public key, Base64URL no-padding, served at `/vapid_public.json`. Consumed by **browser** code. |

If the private key on the server is rotated (e.g. a new deploy
environment), regenerate BOTH files and redeploy the bundle — the
two halves are a matched pair and nothing else.

## What this module does NOT do

- It does **not** silently re-subscribe on token rotation.
  `PushNotificationService.subscribeIfPermitted()` only runs from a
  user gesture (Play button, Resume click). On push-side token
  rotation, the server's `PushSubscriptionStore` still has the old
  endpoint and 404/410s the new push. Cleanup is on the
  `PushNotificationService.sendTurnStart` switch arms at line 105.
- It does **not** work in headless Chromium with
  `Notifications.requestPermission()` rejected (which `grantPermissions`
  in Playwright cannot fully override). The push-turn-start e2e probe
  works around this by injecting the subscription server-side via the
  `/debug/seed-push-subscription` debug endpoint — see
  `kvisionApp-e2e/README.md`.
